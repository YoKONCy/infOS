## 1. 目标与已确定方向

- 据点按房间区分群聊模式与协作模式。
- 群聊模式以角色扮演、日常聊天、成员互动为主，保留现有体验。
- 协作模式支持明确目标、成员分工、协作状态机、定向通信、成果交接和验收。
- 协作能力融合 AIOS 的身份、上下文编译、执行归属和权限架构，复用统一 ContextCompiler。
- 参考 Varin 的负责人委派、独立成员 Thread、定向消息及成果交接；具体实现遵循 infOS 的后端、存储和角色体系。
- 负责人、执行者、复核者是任务内职责；PrincipalAgent 的身份、人设和个人记忆仍保持独立。
- Stronghold 继续属于主应用内部模块；沿用 `group` Channel，不注册 Application Realm，不为协作新增 Channel。

## 2. 现状与缺口

| 方面 | 当前基础 | 后续需补齐 |
| --- | --- | --- |
| 据点 | 房间权威消息流、成员管理、回应调度 | 房间模式及协作入口 |
| 成员上下文 | `stronghold_${roomId}_${agentId}` 对应独立成员 Thread | 协作任务维度的隔离与显式绑定 |
| 上下文编译 | ContextRegion Provider、预算选择、来源与 Manifest | 协作视角 Provider、可信任务作用域、统一最终组装 |
| 执行身份 | Kernel Execution 生命周期与身份记录 | 持久化协作调度、依赖推进、恢复与幂等交接 |
| 工具权限 | Agent / Channel 能力门控及 group 工具限制 | 经授权的协作工具与工作能力策略 |
| 展示 | 房间消息流与内部成员 Thread 分离 | 分工、进度、阻塞、成果与验收的聚合投影 |

当前据点在 ContextCompiler 编译后仍追加部分房间与视角内容；协作接入时需一起收敛到可计费、可审计的上下文组装路径。

当前详细工作上下文主要面向 `desktop + work`，group 还有固定工具限制。不能假定开放一个协作入口后就已具备完整工作能力。

现有 Kernel Execution 记录能力不能直接等同于具备持久恢复能力的多 Agent 调度器。需核查并复用任务执行、队列、取消与修订守卫，补充协作编排所需状态。

## 3. 分层与数据归属

建议关系：

```text
据点 Room（群聊 / 协作）
└─ 协作任务 CollaborationRun
   ├─ 目标、任务修订、负责人、权限及验收要求
   ├─ 成员分工 Assignment 与依赖关系
   │  └─ 成员 Thread → 多轮 Execution
   ├─ 定向消息与处理回执
   └─ 成果引用、版本与验收结果
```

- 协作服务维护任务与分工的持久化事实；Repository 负责存储，Router 只负责输入校验及调用。
- ContextCompiler 读取事实并编译当前轮次，不承担调度、状态写入或工具执行。
- 复用现有 Task / Execution / Queue；协作分工与底层执行建立显式关联，避免出现两套互相矛盾的执行状态。
- 复用已有任务计划表达步骤与展示进度；计划勾选不能替代执行结果或成果验收。
- 每个协作任务拥有独立状态机；不同房间、不同任务、不同成员的运行状态不能共享可变全局实例。
- 主应用显示的活跃角色不决定后端执行主体。执行必须绑定真实 `agentId`、`threadId`、任务与成员身份。
- 房间模式、Thread 的 `interactionMode`、`executionMode` 及成员职责分别建模，禁止混为一个全局 mode。

## 4. AIOS 上下文融合

### 4.1 每位成员获得独立视角

| 组成 | 注入原则 |
| --- | --- |
| 身份与人设 | 保留所属 PrincipalAgent 的身份；任务职责作为附加上下文 |
| 目标与分工 | 当前目标、本人任务、验收标准和必要限制优先保留 |
| 协作状态 | 按职责提供依赖、相关进度、阻塞及待决策事项 |
| 成员消息 | 只提供当前成员有权读取且与任务相关的消息，保留来源 |
| 成果 | 提供摘要、版本与引用；长文和文件按需读取 |
| 历史 | 使用本次任务的成员 Thread；复用分支须显式绑定任务 |
| 个人记忆 | 按本人权限与任务需要检索，禁止跨 Agent 混库 |

### 4.2 定向通信与输入边界

- `inform`：信息送达后等待成员下一次执行时读取，不自动启动模型。
- `request`：创建处理请求，经调度器在安全输入边界消费；是否排队、唤醒或等待取决于执行状态和权限。
- Agent 消息保留发送者、接收者、所属任务、消息 ID 和关联请求；他方消息不能冒充用户或系统指令。
- 请求方是另一个 Agent 时，不产生新的人工授权；现有权限与审批要求继续生效。
- TODO：设计持久化收件箱、幂等键、处理游标与回执，区分已接收、处理中、已处理、失败。
- TODO：仅在对应轮次结果成功持久化后推进已处理游标；恢复重放不能产生重复副作用。
- TODO：明确忙碌、暂停、取消、等待用户、成员离线时的消息处理规则；新消息不直接改写进行中的输入快照。
- TODO：限制递归委派、互相唤醒、循环依赖、并发量、轮次数和预算，避免无限对话或死锁。

## 5. 协作生命周期与成果闭环

建议任务状态包括准备、执行、等待输入、阻塞、待验收及完成 / 失败 / 取消；成员分工拥有自己的排队、执行、等待和提交状态。最终状态名与迁移规则在实施前定稿，不要求每个任务机械经过全部阶段。

- TODO：定义状态迁移表、转换条件、责任主体及失败原因；明确负责人能调整什么、哪些变更需要用户确认。
- TODO：任务目标修改产生修订；旧执行结果须经过修订检查，避免覆盖新的任务要求。
- TODO：任务提交与验收分开。成员报告完成不代表成果已通过验收，模型文字不能直接覆盖真实执行状态。
- TODO：持久化分工、依赖、消息、成果引用、回执和恢复检查点；重启后核对执行实际状态再推进。
- TODO：明确暂停、恢复、重试和取消的传播范围，防止父任务结束后成员执行失去归属。
- TODO：为依赖失败、成员不可用、超时及部分成果定义继续、重新分配、等待或终止策略。
- TODO：成果记录提交者、来源 Execution、版本及验收意见；通过引用分享，避免复制完整内部对话或推理。
- TODO：共享文件仅授予明确的资源范围；文件写入与成果合并处理版本冲突，禁止静默覆盖其他成员修改。
- TODO：并发预算与资源释放统一归属明确的任务 / 执行；关联 ID 只表达因果关系，生命周期策略显式定义。

## 7. 建议实施顺序

1. **合同与边界**：确认对象关系、状态迁移、任务修订、权限和 Thread 隔离方案，盘点现有 Task / Queue 的复用点。
2. **上下文接入**：实现可信作用域、成员视角 Region、统一预算 / Manifest 与 group 能力策略，保留群聊行为。
3. **最小协作闭环**：一名负责人向一名成员委派，成员独立执行并提交成果，由负责人验收；支持取消与失败反馈。
4. **持久恢复与并发**：补齐收件箱 / 回执、崩溃恢复、依赖、重试、多个成员并行和冲突处理。
5. **界面与迁移**：实现双模式入口、协作投影与历史展示，更新正式架构和功能文档。

阶段顺序为规划建议；正式实施前需先定稿数据合同，不能以界面演示代替后端执行闭环。

## 9. 实施前待确认

- 首版成员规模、并发上限、预算默认值及负责人选择 / 转交方式。
- 成员 Thread 按分工创建或按任务成员复用，以及再次委派时的分支规则。
- 房间能否同时承载多个协作任务，是否允许空闲时切换模式，切换后的历史展示方式。
- 成果验收默认由负责人还是用户完成，以及自动验收的授权范围。
- 共享工作目录与个人 Workspace 的映射、成果发布及文件合并策略。
- 首版先复用现有 PrincipalAgent；临时执行 Agent 的身份与生命周期如需支持，另行设计。
